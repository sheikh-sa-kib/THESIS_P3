# Simulation Validation — Midtown Manhattan Network

## 1. Network Topology

| Metric | Count |
|--------|-------|
| Total edges (SUMO `<edge>` elements) | 1,130 |
| Non-internal edges (`<edge id="...">` without leading `:`) | ~1,130 |
| Total junctions (`<junction>` elements) | 715 |
| Non-internal junctions (actual intersections) | ~700 |
| Network bounding box | ~4.75 km × 2.69 km |
| Source | OSM export (manhattan.osm) via `netconvert` |
| Projection | UTM zone 18N |

The network covers midtown Manhattan from approximately 40.745°N to 40.765°N, bounded by -74.000°W and -73.970°W. Edges are filtered for `passenger` vehicle class only; isolated edges are removed.

## 2. Existing Route File

| Metric | Value |

The route file is generated by `randomTrips.py` with `--period 2.0 --end 60.0`, producing 30 vehicles departing every 2 seconds. This is a minimal validation set.

## 3. Recommended Vehicle Counts

For a 300–500 step simulation with 1-second step length:

| Scenario | Vehicles | Departure period | Rationale |
|----------|----------|------------------|-----------|
| **Light** | 60 | 5 s over 300 s | Minimum viable for algorithm comparison; no congestion |
| **Medium** | 150 | 2 s over 300 s | Moderate congestion; meaningful rerouting pressure |
| **Realistic** | 300 | 1 s over 300 s | Approximates light urban traffic (~63 veh/km/lane) |
| **Stress** | 500 | 0.6 s over 300 s | Heavy traffic; tests emergency response and congestion handling |

### Rationale

- **Network capacity**: With ~1,130 edges and ~700 junctions, the network can support hundreds of simultaneous vehicles without saturation. A typical Manhattan grid street carries ~500–1,000 veh/hour/lane in free flow.

- **Departure rate**: 1 veh/s (300 over 300 steps) deposits vehicles gradually. Even at peak concurrency, with vehicles traversing 10–30 edges each, the number simultaneously on the network stays well under edge count.

- **Avoiding teleportation**: SUMO teleports vehicles when they cannot enter the network due to gridlock. At 300 vehicles over 300 steps, teleportation is unlikely. At 500+, it may occur under heavy rerouting. The stress scenario tests this boundary deliberately.

- **Computational feasibility**: Each algorithm run for 300 steps with 300 vehicles requires:
  - ~60–180 routing calls (one per reroute interval)
  - Each call processes a graph of ~700 nodes / ~1,130 edges
  - Estimated wall-clock: 30–120 seconds per algorithm on modern hardware

## 4. Recommended Default for Experiments

**300 vehicles, 300 steps, 1-second departure interval** — balances:
- Sufficient density for rerouting events to occur
- Low teleportation risk
- Fast iteration for multi-algorithm comparison
- Represents a realistic light-urban traffic scenario

## 5. Algorithm-Specific Considerations

| Algorithm | Complexity | Expected impact at scale |
|-----------|-----------|-------------------------|
| Dijkstra | O(E + V log V) | Baseline; fast on this graph |
| A* | O(E + V log V) | Slightly faster than Dijkstra with good heuristic |
| ACO | O(N_ants × V²) | Slower; 10–20 ants, 50–100 iterations recommended |
| BCO | O(N_bees × V²) | Similar to ACO; 10–20 bees |
| PSO | O(N_particles × V²) | Similar to ACO; 20–30 particles |
| E3-Hybrid | O(N_swarm × V² × 3) | Slowest due to 3 sub-swarm evaluations; use 10 per sub-swarm |

For 300 vehicles, all algorithms are expected to complete routing within 10s timeout.

## 4. Emergency Event Configuration

Insert 3–5 emergency events randomly between steps 100–250:
- Each blocks 2–5 adjacent edges
- Duration: 50–100 steps
- Triggers rerouting for affected vehicles

This creates measurable rerouting pressure without destabilizing the entire network.

## 5. Teleportation Monitoring

Teleportation is the primary indicator of unrealistic saturation. The experiment must record:
- Vehicles that are teleported
- Step numbers of teleport events
- Reason (gridlock, stuck, timeout)

If teleport rate exceeds 5% of vehicles, reduce vehicle count or increase departure spread.
